## Анализ доработок

### 1. 🟡 Выбор породы (+ пол) на 1-й странице

**Сейчас:** в примере cow-keypoints есть `cow_breed` как свободный `text_input`, поля пола нет. Типы полей платформы: только `text_input`, `datetime`, `instruction`, `camera_photo`; dropdown/select нет.

| Вариант | Что делать | Плюсы | Минусы | Когда имеет смысл |
| --- | --- | --- | --- | --- |
| **A. Оставить text_input** | Порода и пол: свободный текст / подсказки | Без разработки платформы | Опечатки, нет единого справочника, плохо для аналитики и ветвления | Быстрый пилот |
| **B. Новый тип поля select / single_choice** | Schema + Flutter + билдер: список пород (прил. 1) и пол Бык/Корова | Чистый UX, валидные значения, удобно для ветвления и отчётов | Нужна доработка платформы | Целевой вариант |

**Вывод:** для справочника пород и дальнейшего ветвления нужен **B (select)**. A только как временный костыль.

### 2-5. 🔴 Несколько форм в одном проекте (вместо ветвления)

**Сейчас:** одна линейная форма на проект (`collector/config.json`). Ветвления нет. Один проект = одна БД + один S3.

**Решение (зафиксировано):** не `show_if` и не 3 проекта на хозяйство. В **одном проекте** несколько **форм**; оператор после входа в проект выбирает форму (это и есть выбор типа животного / сценария сбора). Пакеты и storage остаются в рамках проекта.

#### Договорённости

| Тема | Решение |
| --- | --- |
| Хранение форм | Отдельные файлы в Git: `collector/forms/{form_id}/config.json` (вариант A). Текущий одиночный config мигрируем в форму (напр. `default`) |
| Выбор в мобилке | Отдельный экран после проекта: только **название** формы. После выбора сценарий как сейчас (шаги → review → пакет) |
| Кто выбирает тип | Оператор сам (форма = тип сценария / животного). Ветвления внутри формы **нет** |
| Пакет | В манифесте: `form_id` (+ отображаемое имя при необходимости). `field_id` уникальны **в рамках формы**. Старые пакеты без `form_id` → форма по умолчанию (`default`) |
| Админка | Пакеты в рамках проекта; фильтр/колонка по форме; редактирование данных по схеме **этой** формы |
| Viz / pipeline | Не один жёсткий `viz.json` навсегда: несколько визуализаций; у каждой список `form_ids` (одна viz → несколько форм, или разные viz на разные формы) |
| MVP контента krs-label | Пока **не** режем на бык/молодняк/корова. Делаем механизм абстрактно; текущий конфиг становится одной формой |
| Шкалы (п.5 заказчика) | Это не отдельная фича платформы: разные шкалы = **разный контент полей** в разных формах, когда будем заводить формы под типы животных |

#### Git layout (целевой)

```
collector/
  forms/
    default/
      config.json          # как нынешний project JSON (fields, flow, ui)
    # позже: bull/, young/, cow/, ...
  media/
  visualizations/          # или collector/viz/*.json
    keypoints.json         # { "id", "title", "form_ids": ["default", "..."], "layers": [...] }
```

Обратная совместимость чтения: если есть только старый `collector/config.json` без `forms/`, сервер считает это одной формой `default`.

#### API / синк (как лучше для offline-first)

- `GET /v1/projects` → у проекта краткий список форм: `{ form_id, name, version }`
- `GET /v1/projects/{id}/forms` → полный набор конфигов всех форм (один ответ для кэша на устройстве)
- либо `GET .../forms/{form_id}/config` точечно; для мобилки предпочтительнее забрать **все формы проекта сразу** при синке (офлайн)
- Загрузка пакета без изменений по storage; в manifest обязательно `form_id`

#### Плюсы / минусы выбранного пути

| Плюсы | Минусы |
| --- | --- |
| 1 проект = 1 хозяйство / 1 БД / 1 S3 | Нужна доработка платформы (Git layout, API, мобилка, админка, билдер) |
| Нет `show_if`, проще тестировать каждую форму | Оператор может выбрать не ту форму |
| Viz/pipeline явно привязаны к form_id | Миграция старых config + старых пакетов |
| Масштаб на новые хозяйства: клон проекта с набором форм | |

**Спека:** [specs/10-project-multiple-forms.ru.md](../../specs/10-project-multiple-forms.ru.md) · [EN](../../specs/10-project-multiple-forms.md)

### 6. 🟡 «Высота в крестце» и «вес» после inference

**Сейчас:** вес: ручной `cow_weight` (text). Высота в крестце: не поле формы. После inference значения в пакет оператору не пишутся и в мобилке не показываются (distances есть в админ-визуализации).

**Заказчик хочет:** после inference записывать «высоту в крестце» и «вес» в пакет и показывать оператору.

| Вариант | Что делать | Плюсы | Минусы |
| --- | --- | --- | --- |
| **Единственный: писать из inference в пакет + показ оператору** | Пайплайн после inference кладёт значения в пакет; UI показывает их оператору | Соответствует запросу заказчика; один источник: промеры по фото | Нужно добавить: запись в пакет, доставка на клиент, отображение. Другого варианта нет |

**Вывод:** другого пути нет: добавляем запись результатов inference в пакет и показ оператору.

### 7. 🔴 Расчёт веса по фото (must have)

**Сейчас:** модели/этапа оценки веса нет. Есть keypoints inference и distances; вес: ручной ввод.

| Вариант | Что делать | Плюсы | Минусы |
| --- | --- | --- | --- |
| **A. Серверный пайплайн (datapipe)** | Модель веса → результат в `inference_json` / поле пакета → админка (+ мобилка) | Единое место для ML; не раздувает APK | Нужен бэкенд/пайплайн. По качеству это скорее **регрессия** относительно наших текущих размеров и фич |

**Вывод:** вариант только **A**. Ожидаемо хуже наших текущих промеров/фич по качеству: закладываем как must have заказчика с этим риском.

### 11. 🟢 Сжимать 4K только для отображения в браузере

**Сейчас:** админка показывает/декодирует оригиналы; в storage лежат полные файлы.

| Вариант | Что делать | Плюсы | Минусы |
| --- | --- | --- | --- |
| **Сжатие только на фронте в браузере** | При показе в UI даунскейлить/сжимать в браузере; originals в S3/upload не трогать | Быстрее UI, исходники для ML целы | Тяжёлый blob всё равно скачивается до сжатия на клиенте |

**Вывод:** сжимать только для фронта в браузере, исходники не менять.
